
### 1. Collections and Schema Definitions

The application uses three primary MongoDB collections: **Users**, **Projects**, and **Tasks**. 

#### **User Collection**
| Field | Type | Modifiers / Defaults | Description |
| :--- | :--- | :--- | :--- |
| `name` | String | Required | Full name of the user. |
| `username` | String | Required, Unique, Trimmed | Unique identifier for login. |
| `email` | String | Required, Unique, Lowercase | User's email address. |
| `password` | String | Required | Hashed password (using bcrypt). |
| `role` | String | Enum: 'Manager', 'Member' (Default: 'Member') | Determines system permissions. |
| `timestamps` | Date | Auto-generated by Mongoose | `createdAt` and `updatedAt`. |

#### **Project Collection**
| Field | Type | Modifiers / Defaults | Description |
| :--- | :--- | :--- | :--- |
| `name` | String | Required, Trimmed | Title of the project. |
| `description` | String | Required | Details about the project goals. |
| `owner` | ObjectId | Ref: 'User', Required | The Manager who created the project. |
| `members` | [ObjectId] | Ref: 'User' | Array of team members with access. |
| `isArchived` | Boolean | Default: false | Soft-deletion flag to hide inactive projects. |
| `timestamps` | Date | Auto-generated by Mongoose | `createdAt` and `updatedAt`. |

#### **Task Collection**
| Field | Type | Modifiers / Defaults | Description |
| :--- | :--- | :--- | :--- |
| `title` | String | Required | Task headline. |
| `description` | String | Required | Detailed task instructions. |
| `status` | String | Enum: Backlog, In Progress, In Review, Done, Blocked. Default: Backlog | Current lifecycle stage. |
| `previousStatus` | String | Enum: Same as above (Default: null) | State before blocking, used to revert. |
| `priority` | String | Enum: Low, Medium, High (Default: Medium) | Importance level. |
| `dueDate` | Date | Optional | Deadline for the task. |
| `project` | ObjectId | Ref: 'Project', Required | The parent project this belongs to. |
| `assignedTo` | [ObjectId] | Ref: 'User' | Users responsible for the task. |
| `dependencies` | [ObjectId] | Ref: 'Task' | Tasks that must be 'Done' before this one. |
| `dismissedBy` | [ObjectId] | Ref: 'User' | Tracks who has dismissed the overdue alert. |
| `history` | [Object] | Embedded sub-document | Immutable audit log (action, details, user, date). |
| `timestamps` | Date | Auto-generated by Mongoose | `createdAt` and `updatedAt`. |

### 2. Relationships

* **One-to-Many:**
    * **Project to Tasks:** A project contains many tasks, but every task belongs to exactly one project (`project` reference inside the Task schema).
    * **User to Owned Projects:** A user (Manager) can own many projects, but a project has only one `owner`.
* **Many-to-Many:**
    * **Users to Projects (Members):** A project has many members, and a member can belong to many projects (handled via the `members` array in the Project schema).
    * **Users to Tasks (Assignments):** A task can have multiple assignees, and a user can hold many tasks (handled via the `assignedTo` array in the Task schema).
    * **Tasks to Tasks (Dependencies):** A task can depend on multiple other tasks, and one task can block several others (handled via the `dependencies` array).

### 3. Constraints: Database vs. Application

**Enforced by the Database (Mongoose/MongoDB):**
* **Structural Integrity & Types:** Field types (String, Date, Boolean), required fields, and unique constraints (emails/usernames). 
* **Enums:** Restricting `status`, `priority`, and `role` to exact strings.
* **Why here?** The database is the last line of defense. Enforcing basic types, uniqueness, and enums here guarantees dirty data cannot enter the system, even if a backend API check is bypassed or bugged.

**Enforced by the Application Code (Node.js/Express Controllers):**
* **The 5-Stage Task Lifecycle:** Ensuring tasks only move in legal directions (e.g., rejecting a jump from *Backlog* straight to *Done*).
* **Dependency Blocking:** Checking if all tasks inside the `dependencies` array are marked as 'Done' before allowing a task to complete.
* **Auto-Unassignment:** When a manager removes a member from a project, the controller triggers a query to remove that member from all tasks within that project.
* **Why here?** Complex business logic requires reading external context (like querying other tasks to check their status). Handling this in the application layer allows us to return highly specific, human-readable error messages (e.g., "Cannot complete, waiting on Task X") rather than relying on obscure database-level trigger failures.

---

### 4. Deliberate Denormalization

* **`previousStatus` on the Task:** Instead of performing an expensive query through the `history` array to figure out what state a task was in before it became 'Blocked', I denormalized this data by storing `previousStatus` at the top level of the task document.
* **Embedded `history` Array:** Rather than creating a separate `AuditLog` collection and joining it using an ObjectId reference, I embedded the history directly into the Task document. Since task history is almost exclusively read *with* the task, this saves a costly database `$lookup` (join) operation and ensures the frontend loads the task view instantly.

---

### 5. What breaks first at 100x the data?

1.  **The Embedded `history` Array:** MongoDB has a hard 16MB limit per document. At 100x scale, long-running tasks with thousands of automated status changes, due-date updates, and comments will cause the document to hit this limit, crashing task updates. This would eventually need to be normalized into a separate `TaskEvents` collection.
2.  **Global Task Search (`$regex`):** The `getGlobalTasks` controller uses `$regex` for title and description searches. At 100x data, running regex scans across millions of documents without a dedicated Text Index or a search engine (like Elasticsearch) will result in full-collection scans, spiking CPU usage and bringing the database to a crawl.
3.  **Unbounded Arrays (`members` and `assignedTo`):** If enterprise clients use this and add thousands of users to a single project, the arrays will degrade read/write performance.
